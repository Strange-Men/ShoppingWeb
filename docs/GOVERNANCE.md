# 文档治理规范

版本 v0.2；自 2026-11-03 起执行。已从文档基线进入 P1 实现；治理规则持续有效。目标是让业务要求、技术依据、实现与验收保持一致，方便后续开发延续上下文。

## 权威与职责

业主负责业务事实、品牌、素材归属、联系方式和范围决策。开发执行方负责调研证据、技术建议、实现与验证记录。PRD 是需求唯一来源；DECISIONS 记录来源和开放事项；参考站分析记录观察与推断；ACCEPTANCE 记录对应验证。

对话出现新的明确指示时，及时更新相关文档。已授权范围内的可逆文档、研究和实现工作继续进行，不因常规技术细节重复索要批准。涉及未提供的业务事实时留空，不能替业主编造。采购和账号配置需实际资源信息，文档完成不代表资源已购。

## 文件规则

文档用 UTF-8 Markdown，日期 YYYY-MM-DD，业务时区 Asia/Shanghai。机器采集时间允许 UTC，但必须显式标识。每个正式文档包含标题、版本、日期和状态；目录变动同步索引。二进制素材不用于存正文和业务决定。

需求编号 FR-001 起、非功能编号 NFR-001 起保持稳定，删除时标记废弃而不是复用。业务决策 D、技术建议 T、问题 Q 分开编号。ADR 记录关键技术选择和重评估条件，不将建议伪装成已批准。

## 变更流程

1. 记录请求或事实来源，确认属于当前范围还是新增需求。
2. 修改 PRD 及受影响的设计、素材、语言和部署文档；同步决策及验收表。
3. 在 CHANGELOG 说明变化及状态，不把计划写成已经实现。
4. 运行 `node scripts/validate-docs.mjs`，修复本地相对链接与覆盖缺失。
5. 提交到指定仓库，以清晰提交说明标识文档或代码变化。使用 PR 时按模板说明业务变化、验证及仍未执行项。

小的措辞修正无需新增 ADR。改变运行架构、存储、表单、发布地域或翻译机制时更新／新增 ADR。后续版本命名：v0.1 前期文档，v0.2 英文预览基线，v1.0 英文生产基线，后续版本按实际发布记录，不提前宣称版本已交付。

## 证据规则

每项技术判断给出公开原始 URL 和查询日期。优先官方文档，社区文章不能当作同行实际技术栈的证据。对参考站明确区分“观察”“推断”“未验证”；HTTP 头和版本参数都是声明，不能推导出私有配置。

研究脚本只读取已知公开资源，不登录、不提交表单或访问私有接口。仓库保存事实性元数据和哈希，不提交同行整页 HTML、完整业务文案、联系方式、图片或第三方插件完整源码。原始响应仅在忽略目录保留供本地复核。研究结果变更后人工复核分析，不自动修改业务要求。

## 公开仓库与资源

仓库当前为公开可见。仅提交计划对外发布的资料；服务器私钥、密码、API token、环境文件及内部客户资料不进入 Git。图片需符合业主使用授权，同行页面作为参考而不是产品运行依赖。无需改变仓库公开状态。

文档检查工具不自动验证外部链接可访问，不表示浏览器、生产、网络和法律授权检查已经通过。所有测试报告写环境、版本、方法和实际结果；未执行项如实列出。

## 交付定义

P0 文档基线已交付；P1 网站交付还须有实际代码、成功构建、本地页面与交互证据，以及仓库同步结果。本轮结果见[实现状态](IMPLEMENTATION_STATUS.md)和[验收矩阵](ACCEPTANCE.md)。P1 通过不等于 P2 已正式上线，也不等于翻译、真实素材性能或海外网络验收通过。
